Memory and context that survives the session

Agent Workbench is a local MCP server and CLI. It gives every agent session on your machine a persistent cross-tool brain, a full-text index of your repos, and a report on whether its own setup is broken.

20 MCP tools, each with a CLI twin. Stdlib-only Python, no third-party packages. No LLM calls and no network calls: every import is from the standard library, and none of them opens a socket.

Read the install steps Source on GitHub

What it puts on the machine

Three stores, one SQLite state directory, no service to run. The agent talks to them over MCP; you can talk to them over the CLI.

A brain that outlives the session

Durable notes, one of seven kinds: decision, fact, gotcha, preference, todo, note, or reference. They live in SQLite FTS5 with the porter tokenizer, in a file every harness on the machine reads, so a note stored from Claude Code comes back in Codex.

The repo's own convention is that a note carries a source breadcrumb (a ticket key, a Slack channel and date, a doc name, or a permalink pinned to a commit SHA). That is a convention in the standing instructions, not something the store enforces.

Correcting beats stacking: brain_amend edits a note in place, and supersedes=[ids] hides the notes a new one replaces, so a stale claim cannot resurface as truth.

A lexical code index

One bm25 query across every indexed repo. No embeddings and no API calls, so the same query returns the same rows every time. Incremental refresh skips files whose hash has not changed. Point it anywhere with AGENT_WORKBENCH_INDEX_ROOTS.

Diagnostics for the setup itself

Five local scans: MCP config files, assistant permission allowlists, secrets sitting on disk, oversized state files, and doc paths that point at things no longer there. The agent's environment breaks too, and usually silently.

Install

One requirement: Python 3.10 or newer. Nothing is installed with pip, no API key is asked for, and nothing is downloaded at runtime. setup.sh is a bash script that writes symlinks, so it targets a Unix shell.

  1. Clone and run the setup script

    It is idempotent. Re-run it after a pull and it upgrades in place rather than duplicating anything.

    git clone https://github.com/chud-lori/agent-workbench.git
cd agent-workbench
./setup.sh
  2. Answer the harness prompts

    The script detects Claude Code, Codex, and Gemini CLI by looking for the claude binary and for ~/.claude, ~/.codex, and ~/.gemini, then asks about each one. Answering no to all three exits without changing anything.

  3. What it then does for the harnesses you picked

    Registers the MCP server (user scope for Claude Code, a [mcp_servers.agent_workbench] block for Codex, an mcpServers entry for Gemini CLI). Writes the standing instructions into the harness instruction file inside a marker-fenced block, so a re-run refreshes that block instead of appending a second copy. For Claude Code it also wires the four hooks, symlinks the six skills and three agent types, and sets cleanupPeriodDays in settings.json if it is unset, because the 30 day default deletes session transcripts.

  4. Build the index and restart the agent

    The last prompt builds the code index over your repo root. The MCP server and the hooks load when the agent starts, so restart it afterwards.

Prefer doing it by hand? The per-harness commands are in AGENTS.md under Harness setup. To back out, ./uninstall.sh removes the hooks, the instruction blocks, the symlinks, and the MCP registrations. It never touches .state/, so the brain and the index survive an uninstall.

MCP tool reference

Every tool the server exposes, read from the TOOLS table in agent_workbench/mcp_server.py. Each line gives the MCP name and the CLI command that runs the same code, for shells, cron jobs, and hooks.

Filter is starting. All 20 tools are listed below.

Task start

brief_task CLI: run_cli.py brief "<query>"

One call for a ticket key or feature phrase: code index hits, agent docs, saved brain notes, pinned references, likely repos, and the commands those repos run. When the query mentions prod or deploy it also checks the likely repo against its origin baseline and warns if the checkout has diverged.

Brain

brain_remember CLI: run_cli.py remember

Store a durable note with a kind, a project, and tags. The result can include similar_notes, which is the prompt to amend or supersede rather than stack a near-duplicate. Pass supersedes=[ids] to hide the notes this one corrects.

brain_recall CLI: run_cli.py recall

Search notes by query, project, or kind, or omit the query for the most recent. thread=<key> returns one storyline in chronological order with superseded entries collapsed to stubs. since and until bound by when a note was stored, and accept yesterday, a date, or 7d. Resolved and superseded notes stay hidden unless you ask for them.

brain_amend CLI: run_cli.py amend

Correct a note in place. append adds a dated addendum, replace rewrites the body.

brain_promote CLI: run_cli.py promote

Append a personal note to a shared, git-versioned markdown file (a team playbook or a runbook), and stamp the note so it can never be promoted twice.

brain_resolve CLI: run_cli.py resolve <id>

Mark a note done. It is kept and hidden from default recall, because the history of a todo is worth more than its absence.

brain_forget CLI: run_cli.py forget <id>

Delete a note by id. Ids come from brain_recall.

brain_export CLI: run_cli.py export

Dump every note, resolved ones included, as markdown, optionally straight to a file. This is the backup: the brain is the only part of the state directory that cannot be rebuilt.

Code index and docs

code_search CLI: run_cli.py code-search "<query>"

bm25 keyword search over every indexed repo at once.

refresh_code_index CLI: run_cli.py refresh-index

Incremental refresh that skips unchanged files. This is the one to run on a stale-index warning.

rebuild_code_index CLI: run_cli.py index

Full rebuild. Needed after changing the index roots. Writes only inside the workbench state directory.

index_status CLI: run_cli.py index-status

Freshness report: how many repos and documents are indexed, and how many hours old that is.

codebase_overview CLI: run_cli.py overview

Languages, package files, and docs for an indexed repo, or for all of them.

search_knowledge CLI: run_cli.py search "<query>"

Live search over the agent docs themselves: CLAUDE.md, AGENTS.md, SKILL.md, and README files. Read from disk at query time rather than from the index.

find_service_context CLI: run_cli.py service <name>

Given a service name, the likely repo and the commands that repo runs.

Repo and activity

repo_state CLI: run_cli.py repo-state <repo>

Current branch, ahead and behind counts against origin/main or origin/master, dirty files, how stale the last fetch is, and whether the path is a linked worktree rather than the main checkout. Run it before making any claim about how production behaves from local code.

recent_activity CLI: run_cli.py activity

Commits you made in a window, across every local repo, scanning all branches so unpushed work that gh cannot see still shows up. Linked worktrees fold into their main checkout so nothing is counted twice. Commits only: the server has no network access, so pair it with Slack, calendar, and PR lookups for the rest.

Diagnostics

doctor_report CLI: run_cli.py doctor

Findings from five scans: MCP config files, assistant permission allowlists, secrets on disk, oversized state, and stale doc paths.

mcp_health CLI: run_cli.py mcp-check

Config health for the Codex, Claude, and project-level MCP files on this machine.

work_sources_status CLI: run_cli.py work-sources

Whether the optional connector sidecar (Slack, Google Workspace, Atlassian) is present and healthy. It reports state only and never prints a secret.

No tool name or description matches that filter. Tool names use underscores, as in brain_recall.

Three CLI commands have no MCP twin: context summarises one path, recall-brief returns the compact note lines the prompt hook injects, and mcp-server is what the MCP registration actually runs.

The four Claude Code hooks

Standing instructions make an agent likely to use the brain. The hooks make two thirds of the loop happen whether or not the model cooperates, because the harness runs them, not the model. harness/install_hooks.py wires them, recognises its own entries even if the clone moved, and upgrades them in place.

  1. SessionStart

    Prime

    Prints up to five recent brain notes into the session context, each trimmed to 140 characters, with ids so the agent can pull the full body. Registered with the matcher startup|resume|compact, so the brain re-primes after a context compaction instead of quietly fading mid-session. Timeout 20 seconds.

    It then detaches a background job that refreshes the code index and, if your clone has no uncommitted changes, fast-forwards it with git pull --ff-only. A clone with work in progress is left alone.

  2. UserPromptSubmit

    Recall

    Matches your prompt against the brain and injects up to five one-line hits, ids included. Bodies stay pull-based through brain_recall, so the injection stays small. Timeout 10 seconds.

    The CLI side is threshold-gated: a short or trivial prompt injects nothing rather than noise.

  3. Stop

    Store

    When a turn ends, blocks the stop once and tells the model to save anything durable it learned. If nothing durable came up, the model is told to end immediately, so the extra pass stays cheap. Timeout 10 seconds.

    It blocks once and only once. The hook input carries a flag that is true when the model is already continuing from a previous block, and in that case the hook stays silent, so it cannot loop.

  4. PreToolUse

    Guard

    Matches Bash commands against your own regex patterns and forces an explicit human approval on a hit. The check runs outside the model, so a convincing but wrong chain of reasoning cannot talk its way past it. Timeout 10 seconds.

    Inert by default. The patterns file is per-machine and untracked, and a missing or empty file makes the hook a silent no-op. setup.sh offers to seed it from the shipped example.

All four scripts are best-effort by design and always exit zero. A hook that can break session start is worse than a hook that occasionally does nothing.

Two plain git hooks in harness/git-hooks/ sit alongside them and keep commits attributed to the person who owns the repo, for any assistant rather than one vendor. commit-msg strips Co-Authored-By and "Generated with" attribution lines and says what it removed; pre-commit refuses a commit authored or committed under an assistant or bot identity, or with no email set. They chain to any repo-local hooks, keep real human co-authors, and leave prose that merely mentions these tools alone. Enable them for one repo through .git/hooks, or globally with git config --global core.hooksPath; setup.sh offers both.

Skills and agent types

The hooks capture what happens in interactive work. Skills answer the questions a store of durable facts cannot, and the agent types carry recall into subagents, which get no hooks at all.

/standup
What you did in a day, rebuilt from git commits, PRs, Slack, calendar, and brain notes, as a paste-ready Done, Today, Blockers. The brain is deliberately not the source here: it holds durable facts, not an activity log.
/brain-harvest
Weekly backfill. Scans merged PRs, resolved tickets, and your Slack activity for durable knowledge the hooks missed, dedupes against existing notes, and proposes. Nothing is stored without your approval.
/postmortem
Incident reconstruction from evidence: a timeline from Slack, commits, deploys, PRs, and tickets, then a blameless five whys and a draft with action items.
/why
Code archaeology for one file, function, or line, climbing blame to commit to PR to ticket to Slack to brain. It says plainly when no reason was ever recorded, rather than inventing one.
/pr-review
Reviews a PR, branch, or working diff against the project's recorded conventions plus six axes: comment noise, overengineering, security, algorithmic efficiency, simplicity, and maintainability. Findings cite a numbered rule and carry a concrete fix, and the review closes on a mechanical Gate/Justify/Lock verdict rather than a diplomatic summary. Posting to GitHub is approval-gated.
/meeting-prep
A one-page brief for a calendar event, merged from related Slack threads, tickets, PRs, and notes. It briefs from evidence and does not invent agenda items.
Three subagent types, symlinked into ~/.claude/agents/.
TypeWhat it does
scoutRead-only investigator. Checks recorded memory before searching the filesystem, cites path:line and note ids, and reports notes the code now contradicts.
implementerWrites code against recorded decisions, gotchas, and preferences, follows the surrounding style, and reports the change with proof it works.
adversaryLoads the project's known failure modes first, then hunts for the bug that history says is likely. Reports a finding with a concrete failure scenario, or reports nothing.

A subagent gets no SessionStart priming, no prompt-recall injection, and none of the parent's context. Recall has to live in its own system prompt or it never happens, which is the entire reason these three types exist.

Configuration

Six environment variables, all with defaults. Nothing is hardcoded to a particular machine layout except the state directory default, which is noted below.

VariableDefaultWhat it sets
AGENT_WORKBENCH_REPO_ROOT~/repoWhere your work repos live.
AGENT_WORKBENCH_INDEX_ROOTSthe repo rootDirectories to index. Colon or comma separated.
AGENT_WORKBENCH_PROJECTS_ROOT~/ProjectsSecond root that diagnostics and activity scanning cover.
AGENT_WORKBENCH_STATE_DIR~/Projects/agent-workbench/.stateWhere index.sqlite and brain.sqlite are written. The default is a fixed path, not a path relative to the clone, so set this if you cloned somewhere else.
AGENT_WORKBENCH_WORK_MCP_ROOT~/Projects/work-mcpThe optional connector sidecar that work_sources_status looks for.
AGENT_WORKBENCH_CLAUDE_HOME

~/.codex		Harness config locations the diagnostics read.

The state directory is gitignored. index.sqlite is rebuildable at any time; brain.sqlite is the one file worth backing up, and brain_export is how.

Why it is built this way

Lexical retrieval, not RAG
SQLite FTS5 and bm25. Exact, explainable, and reproducible: the same query returns the same rows, and a miss is a query problem you can see rather than a distance threshold you cannot. Query expansion and synthesis are the model's job, and the model is already in the room.
No LLM calls, no network calls
The package imports only the standard library, and none of those imports opens a socket. Git is shelled out to; nothing else leaves the machine.
The brain is personal, playbooks are shared
Notes are yours and live in your state directory. Teams share through git-versioned markdown, which is what brain_promote writes into. Evidence and one-off details stay personal.
State is local and mostly disposable
Everything lives under the gitignored state directory. The index can be thrown away and rebuilt. The brain cannot, which is why export exists and why uninstall refuses to touch it.
Connector credentials live elsewhere
The Slack and Google Workspace connectors are a separate project, work-mcp. Agent Workbench does not need it and only reports whether it is present, so connector secrets never flow through this codebase.
Worktrees are one repo
A repository is identified by its shared git directory, so a linked worktree folds into its main checkout: commits are counted once, the index keeps one checkout per repository, and repo_state tells the agent when it is standing in a worktree.
